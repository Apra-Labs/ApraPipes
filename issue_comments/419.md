## Analysis and Suggested Implementation

### Problem
RTSPPusher consumes 100% CPU due to non-blocking `pop()` in `FrameContainerQueueAdapter` causing continuous polling loops.

### Root Cause

The issue states the problem is in `FrameContainerQueueAdapter::pop()` using `try_pop()` instead of blocking `pop()`.

### Solution

**Fix 1: Use blocking pop**
```cpp
// In FrameContainerQueueAdapter.cpp (CORRECT)
frame_container FrameContainerQueueAdapter::pop() {
    frame_container fc;
    queue.pop(fc);  // <-- Blocks until data available
    return fc;
}
```

**Fix 2: Add timeout with sleep (if blocking pop not available)**
```cpp
frame_container FrameContainerQueueAdapter::pop() {
    frame_container fc;
    while (!queue.try_pop(fc)) {
        if (shouldStop) return nullptr;
        std::this_thread::sleep_for(std::chrono::milliseconds(1));  // <-- Prevent busy-wait
    }
    return fc;
}
```

**Fix 3: Use condition variable (most robust)**
```cpp
// In FrameContainerQueueAdapter.h
class FrameContainerQueueAdapter {
private:
    std::queue<frame_container> queue;
    std::mutex mtx;
    std::condition_variable cv;
    
public:
    frame_container pop() {
        std::unique_lock<std::mutex> lock(mtx);
        cv.wait(lock, [this] { return !queue.empty() || shouldStop; });
        
        if (shouldStop && queue.empty()) {
            return nullptr;
        }
        
        frame_container fc = queue.front();
        queue.pop();
        return fc;
    }
    
    void push(frame_container fc) {
        {
            std::lock_guard<std::mutex> lock(mtx);
            queue.push(fc);
        }
        cv.notify_one();  // Wake up waiting pop()
    }
};
```
